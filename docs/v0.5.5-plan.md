# OmarCraft 0.5.5 plan

**Status: decided 2026-11-07 (the author: "Build the 0.5.5 and move forwards"); released 2026-11-08
after rows 49 and 50.** It replaces 0.5.4 in the marketplace verification: 0.5.4's request
(omacom/omarchy-plugin-marketplace#14311) is superseded by a new one at the 0.5.5 commit.

## The finding

On #14311 (2026-11-07 20:13 UTC), a marketplace reviewer rated this **Conditional Medium**: at 0.5.4,
`bin/omarcraft` accepted arbitrarily long app names and taglines from the remotely fetched Craft catalog,
cached them and put them unchanged in the state JSON, and `Service.qml` collects and parses the whole
result in the shared shell. If an attacker controlled that catalog or its HTTPS response, one large but
otherwise valid record could cause severe memory pressure or an out-of-memory crash of the shell during
the automatic refresh and state read, before any install: curl's time limit is not a byte limit, and
Quickshell's output collector has no size cap.

Confirmed on the code: the catalog was piped from curl into the parser with no byte limit, the parser
copied the name and tagline as they came, and `state` printed them. The AUR answers had the same gap
(no byte limit, versions and dependency names unchecked).

## The fix

Every input from the network is bounded where it enters, and the panel's data again where it leaves.

| Input | Bound | Measured in 2026-11 |
|---|---|---|
| Catalog download | 256 KB (curl `--max-filesize`, and a hard cut that refuses a longer answer whole) | 19 KB |
| AUR answer | 1 MB, the same way | 10 KB for every tool |
| App id | `[a-z0-9-]`, at most 32 | |
| Name, tagline | at most 48 and 96 characters, no control characters | longest 11 and 41 |
| Colours | `#rrggbb` | |
| Apps from the catalog | at most 64 | 13 parsed (18 upstream) |
| AUR version | `[A-Za-z0-9._:+~-]`, at most 64 | |
| Declared dependency | a package name (`[A-Za-z0-9@._+-]`, at most 128), at most 256 of them | |
| Panel data (`state`) | at most 72 tools, every field re-checked | 9 KB in all |

A record that fails a check is dropped; if nothing valid is left, the built-in list is used. The cache
format becomes 3, so a cache written by an older version (from unchecked input) is checked again once,
at once. No change to the panel (`Service.qml`, `Panel.qml`): with every field bounded, the output it
collects is bounded too.

## Tests and checks

- 234 offline tests (18 new): an overlong name, a control character, a malformed id, the app cap; a
  download exactly at its limit, one byte over, and an endless one; a 30 MB catalog during a real check; a
  well-formed catalog padded past its limit (refused whole: the built-in list stays); an oversized AUR
  answer; malformed AUR versions; dependency names that are not package names; and a cache poisoned the
  way 0.5.4 could have written it.
- Each bound was broken on purpose in a copy (eight breaks), and a test failed each time. The first try
  at the download bound showed the tests could hang instead of fail on an endless answer; the fake
  answers are now finite, and the padded-catalog test tells a bounded download from an unbounded one.
- Against the live catalog and the live AUR, on the author's machine: the check succeeds, the panel's
  data is 9 KB, the state read takes 0.1 s, nothing else changes.
- Marketplace baseline, local scan: review-required, `package-manager` only, no findings.

## Not in this release

The upstream catalog changed its format on 2026-11-06/07 (`SUITE` now holds 18 entries, among them
ArtCraft Studio, written one record per line). OmarCraft's parser reads none of them and uses its
built-in list of thirteen Craft apps, which keeps working. Following the new format, and which new apps
to show, is a separate decision (Studio was left out on 2026-10-17).
