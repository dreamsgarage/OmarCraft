# OmarCraft 0.5.9 plan

**Status: the author's rule of 2026-11-22, then the author's go the same evening for the rest below ("lets
close this pending before release"); built on `v0.5.9-dev` (from `main` = 0.5.8), installed on the author's
machine. Not pushed, not released.**

## Why

On 2026-11-22 SolidCraft had an update (0.45.0 → 0.46.2) and the author clicked its tile to open the version
installed. Since 2026-10-17 (before 0.1.0) a click on an installed app with a newer build asked
*Update ⏎ / Launch instead / Cancel*. In the tiles layout that question sits in the strip under the hero, far
from the tile, so it went unseen, and a second click on the tile ran it: an update terminal opened, the
author stopped it (`last-job.json`: `update solidcraft`, exit 130, interrupted) and the panel read
*LAST JOB FAILED*.

## The rule (the author, 2026-11-22)

> "What I expect is to open the installed version from OmarCraft without triggering update, this was a
> normal behavior before and should never disappear." — "When I click in icon of the app there is only a
> launch action to happen even when there is an update pending."

The first approved design said the same (`v1-design.md`, rows: "The row on the update-ready app keeps its
launch action; the update is reachable from *Update all* or the `u` key only"). The 2026-10-17 amendment of
decision 6 (`approved-plan.md`) added the question on click; 0.5.9 takes that part back. Updates stay
package-exact.

## Changes

1. `Model.primaryAction(app, confirm, job)` holds the rule: an installed app → `launch`, whatever its update
   state and whatever question is open; `wait` only while a running job covers that app (it may be
   half-replaced); an app not installed → `ask-install`, or `run-confirm` when its own install question is
   open (unchanged).
2. `Panel.primary()` (click, `Enter`, the rows' ▶) goes through it. Launching closes any open question, so a
   left click after a right click no longer runs *Remove*.
3. The *Launch instead* button and `launchInstead()` go. The rows' action is ▶ *Launch* on every installed
   app (it showed the update icon on an app with an update).
4. Unchanged: *Update all · u* (one question, *Update ⏎* / *Cancel*), `omarcraft update <id>`, IPC
   `update`, the badges, the UPDATES strip, right-click / `x` to remove, `Enter` running an open question.
5. Docs: spec § 8, design, acceptance, Testing § 6, README, approved-plan decision 6 amended, CHANGELOG,
   manifest 0.5.9.

No visual change in the normal state, so no canvas round: the panel looks the same; the update question
appears only from *Update all*.

## Also in 0.5.9 (the author, 2026-11-22 evening)

The audit of the first approved version against 0.5.8 (same day) found three more things, and the author
noticed MailCraft missing from Office:

6. **ArtCraft's list has not been read since 2026-11-11.** That day ArtCraft moved it from
   `crates/core/src/catalog.rs` to `crates/core/catalog.toml` (craft-launcher f6409da, with a signed copy at
   getartcraft.com). OmarCraft read 0 apps and showed its built-in 20 for eleven days; MailCraft
   (`mailcraft-bin` 0.14.0, a community app, Office) and AniCraft (`anicraft-bin` 0.2.1, Creative), both in the
   AUR since 2026-11-11, never appeared. 0.5.9 reads `catalog.toml` from the same host as before
   (raw.githubusercontent.com), within the same bounds: an entry's own keys only, never its sub-tables'; one-line
   strings and `[r, g, b]` colours only; `official` → suite, `community` → community, any other kind left out.
   The built-in list gains AniCraft and MailCraft (19 apps, the list's order and colours, a test keeps them
   equal). MailCraft's desktop id is its publisher's (`io.github.billsecond.mailcraft`, checked in its release
   archive); both packages unpack the projects' own release archives and need only Arch-repo libraries.
   Cache format 7.
7. **The panel says when the list cannot be read** (*Could not read ArtCraft's app list*, the standing line,
   after a job, a failure and offline). Until now only `list` and `check` said so, and their "since" showed
   the latest failure, not the first.
8. **`✓ Updated` names only the apps whose newer build is installed** after the job (the state read), never
   the job's exit status alone: the case of OmarCraft#1 would have said *Updated WordCraft*.
9. **Acceptance closed with the author** (rows 34–75): PASS where the logs show it (34, 36, 41, 72) or the
   offline tests do (75); n/a where a row was replaced (35, 39), dropped (38), applies only with the repo switch
   on (46, 47, 54) or needs a machine the author no longer has (58, 67). Row 37 joins the run sheet.

Not in 0.5.9: ArtCraft (the former ArtCraft Studio, AI image and video through online providers) stays out;
it is not in ArtCraft's list and the AUR has only a source build.

## Tests

- `tests/model.test.mjs`: 16 new (every case above, both layouts' action, a repo app and a source build with
  an update). The 0.5.8 rule put back into `primaryAction` breaks 8 of them.
- `tests/run.sh`: 3 new checks that `Panel.primary()` calls `Model.primaryAction`, opens no question but an
  install one, and that *Launch instead* is gone. All three fail on the 0.5.8 panel.
- 319 offline tests pass (316 + 3); panel logic 65 (49 + 16). `qmllint`: no syntax error, no new warning.
- For 6–8: the parser tests run on a copy of `catalog.toml` (19 apps, equal to the built-in list) and on
  small hand-written entries (sub-tables, escapes and comments, another kind, a missing colour, a number over
  255, a literal string, the old Rust list reading as none); the bounds tests (a long name, an overlong line,
  a control character, a bad id, MAX_APPS); the unreadable list in `state`, the first failure's time kept,
  MailCraft and AniCraft from the list with their groups, desktop ids and glyphs; the summary line with all,
  one, none landed. 331 offline tests (319 + 12), panel logic 72 (65 + 7). Taking out the sub-table rule
  breaks one test, overwriting the first failure's time breaks two.
