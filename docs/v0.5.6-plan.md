## The fix

- Every check runs `checkupdates` (pacman-contrib), as Omarchy's own update check does, with
  `CHECKUPDATES_DB` pointing to a private copy in `~/.cache/omarchy/omarcraft/checkup-db`: it refreshes
  that copy of the package lists without root and without touching the system's. The catalog's packages
  are then read from the copy (`pacman -Si --dbpath`) into `repo-latest.tsv`, versions checked like any
  network input. A failed check keeps the previous answer.
- An installed tool a repo ships is compared with the newer of the system's lists and that copy, so its
  badge appears as soon as its repo has a newer build. A tool not yet installed still offers what an
  install brings now.
- Apps from Omarchy's repo update alone (next section); tools from the Arch repos keep `↑ system` and
  Omarchy's update.
- *Update all* updates every pending app that updates alone, as before 0.5.6, and runs Omarchy's update
  only when nothing but tools from the Arch repos is pending, instead of doing nothing. Same for the menu
  entry and `omarcraft update` without ids.
- The list is fetched at every six-hourly check (`CATALOG_MAX_AGE_MINUTES` 360).
- Cache format 4, so the first read after the update checks at once.
- README: the apps' own update prompts.

Measured on the author's machine against the real system and the live repos: the full check (catalog,
AUR, repos) 6.1 s in the background, the copy 8.8 MB, the panel's read 0.11 s; WordCraft 0.15.2 to
0.16.0 and GridCraft 0.16.1 to 0.17.0 shown as system updates; the system's own lists untouched.

## Apps from Omarchy's repo update alone (decided 2026-11-08)

The first build sent the two apps to Omarchy's update; it worked (row 52: GridCraft 0.17.0 and WordCraft
0.16.0 at 19:13, with one other package), but the author asked whether an app from Omarchy's repo can
update without the whole Omarchy update, which can be many times bigger and more disruptive than one app.
It can, with a check first. The author: go, keep the behavior and flows as in previous versions, and
watch for issues from library dependencies a package does not declare.

- **Flows as before 0.5.6.** Such an app reads like an AUR one (`source` "bin"): the badge shows the
  version, Enter updates that app, *Update all* takes it. Only its job differs.
- **The job** (`repo_update`): refresh the private copy (`checkupdates`); ask pacman, against it, what the
  update installs (`pacman -Sp --needed --dbpath <copy> --cachedir <empty>`, printing each package and
  its address); go ahead only when that is nothing but the named packages. If it needs anything else,
  nothing is installed, the terminal and a notification name the packages, and Omarchy's update is the
  way (exit 4). The package is installed from its `https` address with `yay -U` (the AUR helper Omarchy
  ships, which elevates), and pacman checks its signature: `RemoteFileSigLevel`, which defaults to
  `SigLevel`, must say `PackageRequired`, or OmarCraft refuses. The system's own sync databases are never
  refreshed, so no other package moves.
- **What remains**: a new build that needs a newer library without declaring it. It would affect that
  app alone (it might not start) until the next full update. To be watched in use, as the author asked.
- **Repos**: `APP_REPOS_RE`, Omarchy's repo only. The Arch repos stay with the system: their packages
  depend on many shared libraries, and Arch does not support updating one of them alone.

Checked on the author's machine: `pacman -Sp` against the private copy printed only GridCraft and
WordCraft, from `https://pkgs.omarchy.org/stable/x86_64/`; Omarchy's server carries each package's
signature file; this system requires package signatures (`SigLevel = Required DatabaseOptional`, no
`RemoteFileSigLevel`); a current app is left alone. A first version of the signature check read
`DatabaseOptional` as optional package signatures and would have refused every update; a test caught it.

## Upgrade paths (2026-11-09)

The author wants every installation on the latest version, so the upgrade itself was tested from each
earlier release. `tests/upgrade-paths.sh` (new) clones each release from GitHub into a throwaway folder,
lets that version leave its own cache and state, runs the steps of `omarchy plugin update` (fetch,
`merge --ff-only`, `omarchy-plugin-validate`) and lets 0.5.6 read and check the old data. All nine pass:
0.1.0, 0.2.0, 0.5.0, 0.5.1, 0.5.2, 0.5.3 (57969bd, untagged), 0.5.4, 0.5.5 and 0.5.6, each landing online
with every tool. The only states that refuse an update are local ones: a file in the plugin folder edited
or copied over, or an untracked file where a release adds one (`omarchy plugin update` then says it
cannot fast-forward); a plugin pinned to a commit still updates. The README told developers to copy a
working tree over the installed plugin with `rsync`, which leaves exactly that state; it now shows a
`git fetch` and `checkout --detach` instead, and the README, the HTML README (which still said the check
prints 0.5.3, through `jq`) and `docs/Testing.md` give the reinstall that clears a refused update.
`docs/index.html` sends the GitHub Pages root to the README.
